# Windows 单一助手：共享会话与语音控制设计

日期：2026-10-09。状态：用户已批准本文；实施计划待审核，尚未进入实施。

## 目标与范围

网页和本地语音是同一个 Yu 的两个入口。切换入口、刷新网页和重启服务后，均能接续同一会话；语音消息和真实执行结果出现在网页，不依赖各客户端复制历史。先完成共享会话，再完成语音控制和稳定性验收。保持 Windows 优先，不包含手机、云同步、EXE 或托盘，不更换现有模型供应商。

既有长期记忆已经共用 SQLite。问题在于网页 useConversation 和本地 VoiceSession 各持有聊天历史；API 使用客户端 history，而不是服务端权威历史。此次不能把全部聊天自动转换成长久记忆，也不能将模型回复当成用户事实。

## 选定方案

推荐并采用后端 SQLite 权威会话，沿用 YU_DB_PATH 对应数据库，新增独立会话表，不修改或删除既有记忆、事件和审计表。实施迁移前用 SQLite 备份接口备份实际数据库，避免在线文件复制不一致。

不采用仅进程内共享：重启会丢失。也不采用网页与监听互相复制：双主写入容易冲突、重复执行。

本轮只提供一个持久默认会话，入口自动绑定同一个 session_id，不增加会话切换界面。后续独立会话能力不在本轮。

## 职责与数据

- ConversationStore：持久保存会话、轮次、返回结果和记忆引用，提供游标增量查询；不调用模型、不执行动作。
- ConversationService：单会话有界队列、请求去重、上下文构建和调用既有路由；在后端决定消息顺序。
- API：薄接口层；网页和本地语音均通过它读写，不直接访问 SQLite。
- 两个客户端：只保留展示缓存、消息编号和待发送状态，不再维护权威 history 或记忆引用。
- VoiceRuntime：唯一麦克风所有者，负责监听、唤醒、控制和播放；使用共享聊天服务，不另建对话大脑。

会话保存 id、创建时间。轮次保存递增序号、session_id、request_id、source（web/local_voice）、用户文本、queued/running/completed/failed/unknown 状态、创建与完成时间、回复及原有业务结果。约束 UNIQUE(session_id, request_id)。记忆引用由最近完成结果提取，客户端省略时由后端恢复；显式提供的引用仍须既有校验。

持久历史与模型上下文分离：数据库保留完整轮次，模型仅取最近 20 条已完成 user/assistant 消息；网页每次最多读取 100 轮，按游标分页。不保存原始录音，不把聊天正文复制到普通诊断日志。

## 接口与顺序

新增 GET /api/conversation 返回默认 session_id；GET /api/conversation/turns?after=序号 返回有序轮次和游标；GET /api/conversation/requests/{request_id} 查询回执。

POST /api/chat 扩展 session_id、request_id、source，保持原回复业务字段。新客户端不再提交 history；默认会话也使用后端历史。旧 history 字段过渡期可解析但不作为共享会话权威数据，不允许客户端历史注入 system 指令。未提供 request_id 的旧调用生成新编号，不承诺幂等。

单会话最多 3 条等待消息。入队前持久记录编号与内容，按入队序处理；处理时读取最新完成历史，而不是提交时的客户端快照。队列满返回明确错误，不执行也不自动重试。相同编号与相同内容返回既有状态/结果；相同编号不同内容返回 409。

HTTP 断开不重复提交动作。超时先查同一编号回执；仍未知就展示“结果待核对”，不能宣称未执行。服务重启后 queued/running 轮次标记 unknown，不自动恢复执行。此方案防止正常运行中的重复提交，不承诺进程崩溃与外部动作之间的严格 exactly-once。

已失败、未知、尚未完成的回复不作为模型事实上下文；已完成的业务失败结果可以接续解释，但明确保留失败字段，不将失败写成成功。

## 网页同步与语音状态

网页加载时读取共享轮次，前台每秒增量轮询，后台降到每五秒；离开页面取消请求。结果按后端编号归并，语音消息和乐观展示不重复。轮询失败显示离线，不覆盖已显示内容；网络恢复后补齐。无需新增 SSE/WebSocket 订阅基础设施。

控制状态接口统一展示待唤醒、连接中、听取指令、处理、朗读、暂停、停止、故障。启动管理器和监听进程向本机 API 发布状态与心跳；超过五秒没有心跳，网页标记状态未知，不继续显示正在监听。只允许本机同源读取与控制，不扩大监听地址；控制写操作要求同源检查和本次启动短期令牌，令牌不写日志、不跨重启复用。

网页保留手动语音作为备用，但检测到本地监听活动时禁用另一采集入口并解释原因，不抢占麦克风。现有服务端语音互斥保留。

刷新页面会恢复共享历史，不再因 useState 初始化而丢失；历史上只存在于已结束客户端内存中的旧消息无法恢复，不臆造迁移数据。

## 语音行为与隐私边界

“结束/结束语音”结束云端对话，回到本地待唤醒；“停止本次服务/关闭语音服务”停止朗读、录音、连接和本次 API；“暂停朗读/别说了”停止当前播放，不宣称撤销已经执行的动作。控制命令优先于聊天和动作队列，讨论控制词不触发命令。

背景声音不能靠音量阈值可靠识别说话人。默认改为一次唤醒接收一个完整请求：收到 final 后关闭该轮上传，不接受新的普通句子；真实回复和朗读完成后回到本地待唤醒。历史仍共享，下一次唤醒无需重新交代背景。连续模式保留为显式可选设置，默认关闭；不引入声纹识别。

朗读改为可取消的受管子进程。播放期间普通识别和云上传关闭，但同一个采集流向本地固定控制语法检测器提供音频；只识别暂停/关闭控制词，不执行普通聊天。检测时先终止当前朗读再处理控制。提示音与朗读需避免自身文本触发控制：对完整控制词句不自动朗读，并用真人扬声器回声测试验收。不能宣称固定语法识别天然消除回声。

本地停止检测只适用于朗读期间；待唤醒仍仅本地检测唤醒词。进入云端识别后控制词走 final 优先分支。未建立识别连接时通过网页停止入口或 Ctrl+C 停止，不能谎称此时所有口头命令可用。

握手、解码器退出/重建、无消费者的清理阶段均暂停入队。帧保留单调时间戳，超过两秒判为过期，结束当前轮并明确报错；不能将旧录音迟到后执行。活动会话发生积压只结束该轮并释放连接，确认采集可用才回待唤醒；设备断开/格式异常属于致命故障，释放麦克风并显示故障，不无限重启。

## 验收与执行拆分

阶段一：共享后端会话与两入口接入。测试网页提交后语音接续、语音提交后网页显示、刷新/重启恢复、记忆指代、并发顺序、去重、队列满、未知回执不重放；临时数据库验证，不污染真实记忆。完成这一阶段才进入语音行为调整。

阶段二：统一状态与语音控制。测试每次唤醒只接收一请求、背景句子不排队、朗读可取消、停止优先、已提交动作不重发、握手/清理无积压、热拔插明确故障、跨入口互斥。保留既有微信窗口和动作回归测试。

阶段三：完整自动测试、前端构建、独立审查和真人验收。真人检查“网页说明背景→语音追问→网页查看”“语音说明背景→网页追问”、微信主窗口、扬声器播放期间暂停/关闭、音乐干扰、结束后再次唤醒及长时间稳定性。没有真人证据时只能称部分完成。

实施期间默认不录音、不连接收费语音服务；真实验证前说明采集与费用。保留全部用户未提交修改，无授权不提交或推送；不删除既有数据。
